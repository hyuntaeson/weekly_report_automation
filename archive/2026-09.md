### 2단계: 데이터베이스 시스템 ✅ 완료

**파일**: `database.py`

**구현된 기능**:
- SQLite 기반 경량 데이터베이스
- 활동 로그 저장 (activities 테이블)
- 주간 요약 데이터 저장 (weekly_summaries 테이블)
- 파일 타입별 통계 저장 (file_stats 테이블)

- 주간 단위 데이터 조회 기능
- 파일 타입별 통계 제공
- 일별 활동량 집계
- 스키마 자동 마이그레이션 (source, details 컬럼 추가)

**데이터베이스 스키마**:
```sql
CREATE TABLE activities (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp TEXT NOT NULL,
    action TEXT NOT NULL,
    file_path TEXT NOT NULL,
    file_type TEXT,
    source TEXT DEFAULT 'filesystem',
    details TEXT,
    created_at TEXT DEFAULT CURRENT_TIMESTAMP
)
```

**주요 유틸리티**: `get_week_start_end()`, `get_activities_by_date_range()`, `get_file_type_stats()`, `get_daily_activity_count()`, `save_weekly_summary()`, `get_weekly_summary()`

### 10단계: 주간보고서 생성 기능 ✅ 완료 (Phase 7, 범위 축소 적용)

**파일**: `report_generator.py`, `templates/weekly_report.md.j2`

**범위 결정 사항** (사용자 확인 완료):
- 포맷: **Markdown + Word(.docx) 2개만** 지원. PDF/HTML은 이번 스코프에서 제외.
- 자연어 처리: **NLTK/spacy 등 ML 라이브러리 사용 안 함.** action/source/file_type 집계 통계를 Jinja2 템플릿에 꽂아 넣는 "구조화된 문장" 방식으로 구현 (가볍고 빠름).

**구현된 기능**:
- `ReportGenerator.collect_weekly_data()` — DB에서 주간 활동 집계 (source별/action별/파일타입별 건수, 일별 추이, 상위 프로젝트/파일, AI 세션 건수, 하이라이트 문장 자동 생성)
- `generate_markdown()` — Jinja2 템플릿 렌더링
- `generate_word()` — python-docx로 제목/기간/요약 표/일별추이 표/하이라이트/파일유형별 표/최근활동 목록 포함한 문서 생성
- `save_report()` — `reports/weekly_report_{시작일}_{종료일}.md`, `.docx` 파일 저장
- `generate_and_save_weekly_report()` — 전체 파이프라인 + `save_weekly_summary()`로 DB에도 요약 저장
- `modern_gui.py`의 `generate_report()`/`preview_draft()`와 실제 연동 완료

**⚠️ 발견된 환경 이슈 (코드 버그 아님, 인프라 문제)**:
생성된 `.docx` 파일을 저장 직후 재검증하면 **사내 문서보안(DRM) 솔루션이 자동으로 파일을 가로채 OLE2/CFB 포맷(암호화 컨테이너)으로 재저장**하는 현상을 발견함. 증거:
- `python-docx` 패키지 자체 내장 템플릿(`site-packages/docx/templates/default.docx`)조차 원래 ZIP 포맷이어야 하는데 OLE2로 변형되어 있음 (`D0 CF 11 E0` 매직넘버) — 코드로 재현 불가능한 외부 요인
- 방금 새로 만든 순수 zip 테스트 파일도 생성 직후엔 정상(`PK\x03\x04`)이다가, 수 초 뒤 재확인하면 OLE2로 변경됨
- `langchain-kr` 저장소의 기존 `.xlsx`/`.pptx`/`.docx` 파일들도 git diff상 원본 대비 150~200KB씩 증가한 것으로 확인 (동일 패턴)
- **결론**: 실제 회사 PC의 (DRM 연동된) MS Word로 열면 정상 동작할 가능성이 높음. 개발 환경에서 python-docx로 재검증만 불가능한 상태 — **별도 코드 조치 불필요, 실사용 환경에서 사용자가 직접 열어서 확인 필요**

### 12단계: 브라우저 확장 프로그램 ✅ 완료 (Phase 9, 범위 축소 적용)

**파일**: `browser_activity_server.py`, `browser_extension/` (manifest.json, background.js, popup.html, popup.js, icons/)

**범위 결정 사항** (사용자 확인 완료):
- Chrome 대상만 (Manifest V3)
- 수집 항목: **방문 URL, 페이지 제목, 방문 시각만**
- 검색기록 추적, 실시간 탭 감지, 확장 자체 설정 UI는 **이번 스코프에서 제외** (on/off 토글만 최소 구현)

**아키텍처**:
1. `browser_activity_server.py` — Python 표준 라이브러리 `http.server`만 사용한 초경량 로컬 서버 (`localhost:5757`). `POST /activity` 엔드포인트로 JSON(`{url, title, timestamp}`) 수신 후 `database.py`를 통해 DB 저장 (source='browser'). 신규 웹 프레임워크 의존성 없음.
2. `browser_extension/background.js` (Service Worker) — `chrome.tabs.onUpdated` 이벤트로 페이지 로드 완료 감지 → 로컬 서버로 fetch POST. 민감 URL 14개 패턴(로그인 페이지, 은행, chrome:// 등) 자동 필터링. 서버 미기동시 조용히 무시(콘솔 warn만).
3. `browser_extension/popup.html/js` — chrome.storage.local 기반 on/off 토글 UI

**통합**: `integrated_collector.py`에 `enable_browser_server=False`(기본 비활성) 파라미터로 선택적 통합. 기존 흐름 깨지지 않음.

**설치 가이드**: `README_BROWSER_EXTENSION.md`에 chrome://extensions 개발자모드 로드 방법 등 안내 작성됨.

1. `flet` 앱(WeeklyPulse 창, pid는 재확인 필요 — 재부팅/재실행시 pid 바뀔 수 있음)을 다시 `--restore-window`로 포커스한 직후 **바로 스크린샷을 찍어서 실제로 WeeklyPulse 화면이 캡처되는지부터 확인**
2. Accessibility tree가 얕아서 element-index 클릭이 안 되므로, **좌표 기반 클릭(`--x`, `--y`)으로 전환** 필요. 스크린샷을 보고 각 버튼의 픽셀 좌표를 파악해서 `orca computer click --app flet --x <x> --y <y> --json` 방식으로 진행할 것
3. 클릭 대상 버튼: Start/Stop Tracking, IDE 수집, Outlook 수집, Slack 수집, **Confluence 수집(신규)**, Generate Weekly Report, Preview Draft
4. 각 클릭 후 `show_snack()` 메시지가 화면에 나타나는지 스크린샷으로 확인 (에러 팝업 여부도 함께 체크)
5. 특히 Generate Weekly Report 클릭 시 `reports/` 폴더에 실제 파일이 생성되는지, Confluence 수집 클릭 시 config의 `enabled:true` 상태로 실제 API 호출이 되는지 (네트워크 지연 있을 수 있음 — sleep 후 재확인 필요)
6. 테스트 완료 후 실행 중이던 `python modern_gui.py` 프로세스는 종료할 것 (백그라운드에 계속 떠있는 상태일 수 있음)

**정리 필요한 임시 파일**: 이번 세션에서 디버깅용으로 만든 `_verify_docx.py`(docx 손상 이슈 조사용, 이미 정리 시도했으나 재확인 필요), `logs/gui_stdout.log`(GUI 실행 로그)는 다음 세션에서 삭제해도 무방.

### 3. 핵심 발견: Excel도 Word와 동일하게 사내 DRM에 의해 OLE2로 재암호화됨
- 사용자가 `보안점검_모니터링계획.xlsx`를 수정했는데 보고서에 반영 안 되는 문제를 조사하던 중, 실제 파일의 매직바이트를 확인해 `D0 CF 11 E0 A1 B1 1A E1`(OLE2 시그니처)임을 확인 — 원래 xlsx는 zip이어야 함
- `openpyxl.load_workbook()` 호출 시 `zipfile.BadZipFile: File is not a zip file` 발생이 원인이었음. Word 파일에서 이미 알려진 사내 DRM 재암호화 현상이 Excel에도 동일하게 적용된다는 것을 이번에 새로 확인함
- 대응: `zipfile.BadZipFile`만 구분해서 잡고, 이 경우 `_drm_blocked_details()`로 "(내용 변경 감지됨 - 사내 보안 정책으로 암호화되어 상세 내용 확인 불가)"라는 fallback summary를 반환 → 최소한 "뭔가 바뀌었다"는 사실은 보고서에 남도록 개선. 단순 PermissionError(파일이 다른 프로그램에서 열려 일시적으로 잠김) 등 다른 예외는 기존처럼 조용히 None 반환 (다음 저장 시 재시도되므로 정상)
- 세 포맷(docx/pptx/xlsx) 모두 동일한 예외 처리 패턴 적용됨

### 5. 브라우저 활동이 한 번도 기록 안 되던 버그 발견 및 수정
- DB를 직접 조회해서 `source='browser'` 행이 지금까지 **0건**이었던 것을 확인 (`SELECT DISTINCT source FROM activities`에 'browser'가 아예 없었음)
- 원인: `modern_gui.py`의 "Start Tracking" 버튼(`start_tracking()`)이 `FileWatcher`만 시작하고, 크롬 확장이 POST하는 로컬 서버(`browser_activity_server.py`, 포트 5757)는 시작하지 않고 있었음. 크롬 확장 자체(manifest.json, background.js)는 정상이었지만 받아줄 서버가 꺼져 있었던 것
- `integrated_collector.py`를 따로 실행하는 경로는 이미 `enable_browser_server=True`로 되어 있어 문제 없었음 — GUI에서 "Start Tracking" 버튼만 누르는 사용 방식에서만 누락돼 있었음
- `start_tracking()`/`stop_tracking()`에 `BrowserActivityServer` 시작/종료 로직 추가로 수정 (`modern_gui.py`)
- **미검증**: 코드 수정은 완료했지만, 사용자가 실제로 GUI에서 재시작 후 브라우징하면서 DB에 browser 행이 실제로 쌓이는지는 아직 사용자 확인 대기 중
